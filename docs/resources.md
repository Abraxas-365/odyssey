# Resources (cut 2b)

An environment can have **resources**: a PostgreSQL database, a Redis cache or a
volume of files. The control plane stores them; the agent makes them in the
cluster (`OdysseyResource`) and the apps that list them get their connection as
environment variables. The names and variables are one contract in
`pkg/resourcekind`.

## Cluster

What the cluster needs, and what the agent says it can do (`Capabilities.resource_kinds`):

| Kind | Needs | Made as |
|---|---|---|
| `postgres` | the CloudNativePG operator (API group `postgresql.cnpg.io`) **and** a default StorageClass | a CNPG `Cluster` named after the resource (database and owner `app`; 1 instance unless its recipe says otherwise, see below) |
| `redis` | a default StorageClass | Secret, PVC, Deployment (Recreate) and Service, all `<name>-redis` |
| `files` | a default StorageClass | a PVC `<name>-files` (ReadWriteOnce) |

A cluster without the operator or the class simply does not list the kind; the
control plane refuses to create it there.

### Recipe settings (catalog, stage 1a cut 4)

A resource is made from a catalog recipe version (`recipe@N`). A basic recipe
(`postgres-basico@1`, …) has no settings: the agent makes the resource as in the
table above. Others carry a **spec** (`pkg/resourcespec`, schema version 1),
sent in `Resource.builtin_postgres` with `spec_schema_version` and written to
`OdysseyResource.spec.postgres` (+ `spec.recipe`, for people reading the
cluster):

| Setting | On create | On a running database |
|---|---|---|
| `instances` (1–5) | `spec.instances` | follows it (CloudNativePG rolls replicas) |
| `major` (16, 17, 18) | `spec.imageName`: the CNPG image of that major, pinned by digest (`resource.PostgresImages`) | **never changes**: a different major fails the resource ("a major upgrade is a migration, not a setting"); the running major is read from `spec.imageName`, else `status.image`, and left alone when neither says |
| `cpu`, `memory` | `spec.resources` (request = limit) | each one the recipe sets follows it; whatever else `spec.resources` holds stays |

What an agent honours it announces in `Capabilities.resource_capabilities`
(`spec/v1`, and `builtin:postgres:instances|version|resources` where it makes
databases); the control plane adds `builtin:<kind>` for each of
`resource_kinds`. It fails closed in three places, each saying which
capability is missing (`RESOURCES_UNSUPPORTED`, "su agente necesita una
actualización"): creating or changing a resource, moving an environment to
another cluster (its resources are checked against the destination), and the
agent itself, which refuses a `spec_schema_version` newer than it knows instead
of making a basic resource. An agent downgraded below what a resource needs
is caught when the resource is read: its status is `failed` with that same
message, whatever the agent reports, until the agent is updated again.

Inside the agent each kind is one **engine** (`agent/controllers/resource/engines.go`:
apply, remove, connection); the controller never switches on a kind elsewhere
(`TestResourceEnginesAreTheOnlyKindSwitch`).

### Install the operator

`make cluster` (the local k3d) runs `make cluster-addons`, which installs
CloudNativePG, pinned by version and URL (`CNPG_VERSION`, `CNPG_URL` in the
Makefile) with `kubectl apply --server-side` and waits for
`cnpg-system/cnpg-controller-manager`. On another cluster apply the same
release manifest, or install it with its Helm chart. The agent notices the API
when it starts: **restart the agent after installing the operator** (it watches
Clusters only if the API exists at start; before that it re-checks every few
seconds, but the control plane learns about the new capability at the next Hello).

### Storage

Volumes are created with the default StorageClass. Size only **grows**: the
request of the PVC (or `storage.size` of the Cluster) is raised; a smaller value
is ignored. Growing needs a class with `allowVolumeExpansion`; without it the
resource reports `failed` ("the storage class does not allow growing volumes").
A class that binds on first use (`WaitForFirstConsumer`, k3s' `local-path`) is
fine: a `files` claim is `ready` while it waits for its first pod.

### Permissions

Destructive verbs live **only inside environment namespaces**, like Secrets:

- The agent's cluster-wide ClusterRole (generated by `make gen` into
  `agent/install/rbac/role.yaml`) gains `odysseyresources` (+status,
  +finalizers) and **only `get/list/watch`** on `persistentvolumeclaims` and
  `postgresql.cnpg.io` `clusters` (the caches and watches need them).
- The per-namespace ClusterRole `odyssey-agent-environment`
  (`agent/install/rbac.yaml`, written by hand; the kubebuilder markers must not
  grant these) gives `create/update/delete` on `persistentvolumeclaims` and
  CNPG `clusters`, `delete` on `deployments` and `services`, and the Secrets
  verbs (the Redis password). The agent binds it with a RoleBinding of the same
  name only in the `odyssey-*` namespaces it created; the admission policy
  refuses it anywhere else. So the agent cannot delete a volume, database or
  workload of `default`, `kube-system` or any other team's namespace
  (`agent/install_test.go`, `TestAgentCannotEraseDataClusterWide`).
- **Upgrading** from an agent that bound `odyssey-agent-secrets`: the agent
  binds the new role at start and never deletes RoleBindings (create-only), so
  TI may remove the stale objects once the new agent runs:
  `kubectl delete rolebinding -A --field-selector metadata.name=odyssey-agent-secrets`,
  `kubectl delete clusterrole odyssey-agent-secrets`, and
  `kubectl delete validatingadmissionpolicybinding,validatingadmissionpolicy odyssey-agent-secrets`.
  Until then they are inert: the old ClusterRole is no longer shipped, but
  `kubectl apply` does not prune it, so it keeps only its old Secrets verbs,
  and only in the managed namespaces where it was bound.

## Agent

- **CRD `OdysseyResource`** (`agent/api/v1alpha1`, `agent/install/crd`), in the
  environment's namespace, named after the resource. `spec`: `kind`, `generation`,
  `storage`, `deleted`. `status`: `observedGeneration`, `phase`
  (`provisioning|ready|failed|deleted`), `message`.
- **Apply** (`desired.Syncer.ApplyResource`): validates with `resourcekind`,
  ensures the namespace, creates or updates the CR. An older `generation` never
  wins. The deletion checks come **before** the generation comparison (the
  control plane restarts generations at 1 when a name is made again after the
  old one was forgotten): a non-deleted spec for a CR whose control-plane
  deletion is in progress (`spec.deleted`) is retried until the CR is gone,
  then created. Errors are reported as a `failed` `ResourceStatus`; they never
  cut the stream.
- **Report**: a full `ResourceReport` after Hello and every `ReportEvery`, and
  deltas when an `OdysseyResource`'s status changes.
- **Controller** (`agent/controllers/resource`): ready means the Cluster's
  `Ready` condition (or `readyInstances >= 1`), the Redis Deployment having an
  available replica, or the PVC being Bound/WaitForFirstConsumer. Redis runs the
  official image pinned by digest, as uid 999, read-only root filesystem, no
  capabilities, seccomp `RuntimeDefault`; its password is generated once and
  read by `secretKeyRef`, never put in a spec or a command line.
- **Delete** (`spec.deleted = true`): the controller deletes everything it made
  (data included), waits until it is gone, sets `phase = deleted`, and removes
  the CR only after the tunnel has sent that report (finalizer
  `odyssey.dev/resource`, annotation `odyssey.dev/deleted-reported`).
  Objects it does not control are never touched. CNPG volumes that outlive
  the Cluster are deleted only if their `ownerReferences` name that CNPG
  `Cluster` (never a claim that merely carries the `cnpg.io/cluster` label).
- **Data is erased only when the control plane says so.** An `OdysseyResource`
  deleted in the cluster by hand (`kubectl delete`) does **not** lose its data:
  the finalizer stays (so the owner, and with it the children, remain), no child
  is deleted, and the resource reports `failed` ("the OdysseyResource was deleted
  in the cluster by hand; its data is kept until it is deleted from Odicea"). A
  non-deleted spec arriving for it is a no-op (not an endless retry). When the
  control plane later deletes it (`deleted=true`), `ApplyResource` sets
  `spec.deleted` on the terminating object (updates are allowed while a
  finalizer holds it) and the normal delete flow above runs. While it is in
  that state, a resize from Odicea is not applied (the resource keeps
  reporting the "kept" failure until it is deleted from Odicea). The guarantee
  covers the default (background) `kubectl delete`: with
  `--cascade=foreground` Kubernetes' garbage collector deletes the dependents
  itself before the owner, finalizer or not, so TI must not use it on an
  `OdysseyResource`. **TI must not
  delete `odyssey-*` namespaces by hand**: Kubernetes removes everything inside a
  namespace regardless of finalizers' intent, so that is data loss the agent
  cannot prevent; it only refuses to erase on its own.
- **Apps**: `OdysseyApp.spec.resources` (`name`, `kind`, `prefix`) comes from
  `App.resources`. Before the Deployment, `resourcesStep` requires each resource
  to exist and be `ready`; otherwise the app stays *progressing* and, after 10
  minutes (`resourcekind.Wait`), fails with reason `resource`
  (`v1alpha1.ReasonResource`): `resource <name> is not ready: <why>`.
  The pod gets, via `secretKeyRef`: postgres `DATABASE_URL`, `PGHOST`, `PGPORT`,
  `PGDATABASE`, `PGUSER`, `PGPASSWORD`; redis `REDIS_URL`; with a prefix `P` they
  are `P_DATABASE_URL`, … A files resource is mounted at `/data/<name>` and
  `FILES_DIR` is that path. Resource variables win over plain env of the same
  name; changing the list rolls the pods. An app with any files resource uses the
  `Recreate` strategy (a ReadWriteOnce volume cannot be mounted twice), and its
  pod gets an `fsGroup` so a non-root user can write.

## Control plane

The `internal/resource` domain decides what exists; the fleet runs it and
release wires it into the app.

- **Model.** `Resource{id, organization, project, environment, name, kind,
  storage_gi, generation, status, created_by, created_at, updated_at}`.
  `status` is `active` or `deleting`. What the cluster observes (`provisioning`,
  `ready`, `failed` + message) is **not stored**: it is read from the fleet
  (`fleet.Resources.ResourceStatus`) whenever the resource is listed.
- **Ports.** `resource.Cluster` (adapter `resourcefleet`, over `fleet.Resources`)
  and `resource.Usage` (adapter `resourcerelease`, over `release` Commands,
  Queries and Usage). In the other direction release asks `release.Resources`
  (adapter `releaseresource`, over `resource.Queries`) whether a resource exists
  before connecting it. No domain imports another's service.
- **Create** → row (`generation 1`) → `ApplyResource` to the environment's
  cluster → event `resource.created` (→ optionally Connect), all in one
  transaction; a failure anywhere (kind unavailable, variable taken) rolls the
  row back. An advisory lock per environment serializes creations so the limit
  of 10 holds.
- **Connect / Disconnect** are release settings revisions
  (`Settings.Resources[{name, kind, prefix}]`), applied as a `config` deployment
  when a release is online. The desired app sent to the cluster carries
  `Resources`; the variables themselves are built by the agent in the cluster.
- **Delete** takes the settings lock (`release.Usage.WithResourceUseLocked`),
  refuses a connected resource, marks the row `deleting` (new generation) and
  sends `deleted=true`. When the agent reports `deleted`, the fleet drops its
  desired row and publishes `cluster.resource_removed`; the subscription
  `resource.forget_on_removed` (composition root) deletes the row and publishes
  `resource.removed`. The row is **removed**, not marked, so the name is free
  again; the trail keeps the history.
- **Resize** only grows (the repository refuses a smaller size too) and bumps the
  generation; the same size is a no-op.
- **Deleting on a revoked cluster.** If the environment's cluster is revoked
  (or its agent never comes back), `Delete` is refused or the row stays
  `deleting`: nobody can confirm the erasure. It completes when IT moves the
  environment to another cluster (`MovePlacement`): the desired resources move
  with their `deleted=true` flag, the new agent creates the object already
  marked deleted, tears it down (nothing to erase there) and reports `deleted`,
  and the row is forgotten as usual. Until then the resource keeps its name.
- **Waiting for resources.** A deploy of an app with resources waits for them
  in `wait_ready` (outer bound: the agent's 10 min + 3 min; an app without
  resources keeps the 5 min of `ReadyTimeout`). A resource that does not
  become ready makes the agent report the app failed with reason `resource`;
  the deployment fails with `RESOURCE_NOT_READY` («Un recurso de la app (base
  de datos, caché o archivos) no estuvo listo a tiempo.») and the agent's
  message as technical detail.
- **Full reports.** The agent sends a full resource report once per tunnel. On
  one, the fleet forgets the status of every resource desired on the cluster
  that the report omits, so the console shows it «preparing» again instead of
  a stale state. A partial report never forgets.
- **MovePlacement.** The data does **not** move with an environment. If IT moves
  an environment to another cluster, that cluster prepares each resource
  **empty** (same name, new volume). Moving data is out of 2b: copy it yourself
  (`pg_dump`/restore) or keep the environment where it is.
- **Out of 2b.** Backups, restores, point-in-time recovery, shrinking, moving
  data between clusters, other engines, sharing a resource between apps or
  environments.
- **Permissions.** Reading `odyssey:projects:read`; create, resize, connect and
  disconnect `odyssey:projects:write`; delete `odyssey:resources:delete` (it
  erases data). The MCP tools `list_catalog`, `create_resource`,
  `create_database` and `list_resources` use the same checks (none of them
  deletes); see docs/catalog.md «MCP».
